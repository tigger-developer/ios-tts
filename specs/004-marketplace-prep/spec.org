- Scope :: *One release per push to master*, beginning at *1.0.0*, then incrementing the patch component. Multiple commits in one push form one release. GitHub's workflow-token commits do not recursively trigger another run. No feature-branch or pull-request publication.

- Design :: A serialized release workflow checks out current master, advances the manifest and source version comment, commits those metadata changes, pushes an annotated version tag, and publishes exactly main.js, manifest.json and styles.css. The initial untagged 1.0.0 manifest is released as-is. Subsequent runs increment its patch. A run-ID commit trailer identifies reruns so they reuse the same release instead of incrementing twice.
- Concurrency :: Queue up to GitHub's 100-run limit without cancelling an active publication. Each run uses master as it exists when the job starts. A concurrent human push that prevents a fast-forward fails visibly; no force push or automatic conflict resolution. A rerun uses its existing tagged release revision where one was already created.
- Recovery :: Existing release assets must match the tagged files before signing. Existing published releases are verified, never overwritten. An incomplete draft requires operator repair before rerun if files are absent or differ. Failed attestations can be rerun without allocating another version.
- Security :: The publishing job needs contents: write through the ephemeral GITHUB_TOKEN. The separate attestation job retains contents: read, id-token: write and attestations: write. Only trusted master pushes publish; actions remain SHA-pinned. No new credentials or authentication setup; local Git retains SSH.
- Provenance :: Reuse the existing attestation workflow through workflow_call and retain manual recovery. Checkout the requested release tag and compare downloaded assets against it. The caller workflow revision remains the provenance build entry point; the tag records the generated version metadata. Signing runs in the same caller workflow because workflow-token publication does not trigger release events.
- Proportionality :: GitHub orchestration and short shell steps suffice; no packaging framework, dependency installation or plugin build is introduced. The existing offline reader tests remain unchanged. Hosted publication/attestation is the requested production operation, not a metered regression suite.
- Publication bounds :: After local verification and paired review, one initial push may publish 1.0.0; permit one remediation rerun, at most 20 status inspections over ten minutes, one asset download and one cryptographic verification per file. No old tag or release replacement.
