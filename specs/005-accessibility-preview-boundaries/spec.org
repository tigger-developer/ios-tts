** Outcome
- Preserve *paragraph boundaries* for native Accessibility Reader.
** Before
- Rendered paragraphs could become *one continuous text block*, impairing highlighting and spoken pacing.
- Permanent shortcut instructions entered the reading content.
** After
- Rendered headings and paragraphs include *explicit breaks*; Help appears *on demand*.
** Changes
- The view and opening controls are named *Accessibility Preview*.
** Unchanged
- The source note, command identity, word limit, native speech and existing modal remain unchanged.
** Edge cases
- Existing breaks and inline markup remain. Preformatted content is not transformed; complex content and iPhone duplication need further validation.
** Decisions
- *Paired implementation* uses the existing HTML presentation. Native companion apps and pop-out windows are outside this change.
** Next step
- Finish the *macOS and iPhone user checks* in the validation record.

** Research and findings
- macOS comparison :: The same prose retained paragraph separation in Apple Notes. A webpage retained paragraphs in Safari but flattened them in Firefox, both normal and Reader modes, and Chromium.
- Inference :: The evidence points to differences in text exposed to or extracted by Accessibility Reader. It does not identify a browser implementation as the proven root cause.
- Controlled fixture :: Three short passages were represented as separate paragraph elements, double explicit line breaks, and preserved blank-line text. Firefox, Chromium and the plugin flattened ordinary paragraph boundaries while retaining internal explicit breaks and preserved newlines. Adjacent headings still joined where no explicit break existed.
- Reading granularity :: The plugin's preserved-newline case highlighted its middle paragraph independently. This established that HTML presentation within the plugin could support separate reading units.
- Native comparison limit :: The Safari result used a normal webpage, not the three-variant fixture. Ordinary Obsidian extraction also included workspace text; its preformatted case differed from the plugin case. These are separate observations, not evidence that every host exposes identical HTML.
- Apple guidance :: [[https://developer.apple.com/videos/play/wwdc2026/219/][Enhance the accessibility of your reading app]] discusses granular text navigation, continuous reading and standard native text components. [[https://developer.apple.com/videos/play/wwdc2025/229/][Make your Mac app more accessible to everyone]] distinguishes containing and combining accessibility elements. Neither establishes that a single element necessarily lacks paragraph structure.
- WebKit reference :: [[https://bugs.webkit.org/show_bug.cgi?id=154098][Paragraph-related accessibility text-marker implementation]] documents paragraph operations at the browser accessibility interface. No special HTML metadata tag was established as a remedy.
- Evidence limits :: Screenshots establish displayed boundaries and highlighting, not audible pacing or end-to-end completeness. The earlier iPhone duplication and footnote-related failures remain separate validation concerns.

* Edge Cases
- Repeated publication must not add another separator pair to an already processed block.
- Empty notes retain normal renderer output. Existing hard breaks, links and emphasis are preserved.
- Preformatted and non-HTML elements are excluded. Late embedded rendering is not newly normalized by a background observer.
- Help starts collapsed for each snapshot and does not create its instructions until activation.

* Solution Design
- Boundary handling :: After rendering, before publication, append two br elements inside each XHTML paragraph and heading. Retain the original elements and their inline children; mark processed blocks to avoid repeat insertion. Remove their bottom margin so explicit breaks supply the trailing spacing.
- Help :: A semantic button outside the article toggles creation/removal of the platform-specific shortcut paragraph. Maintain aria-expanded. Its event listener belongs to the session RenderOwner. No fade timer, rasterized instructions or persistent help state.
- Compatibility :: Keep the command ID and display name, manifest name, settings, snapshot lifetime and focus/isolation behaviour. The modal title, opening-control labels and relevant notices use Accessibility Preview.
- Security :: Fixed DOM additions affect only the snapshot. No new dependency, note write, network access, content logging, speech API or privilege. Obsidian remains responsible for rendering untrusted note content.
- Verification choice :: Retain the 12 session/settings regressions. Native rendering and speech need user validation; no mock accessibility engine or source-matching regression suite is introduced.
