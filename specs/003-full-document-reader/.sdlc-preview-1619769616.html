Full document reader for macOS and iOS

Outcome
Open the whole current note so Apple's Accessibility Reader can read it on macOS and iOS.
Before
For long documents, Obsidian preview loads only a portion for display, so Accessibility Reader cannot access the whole document. At the original starting point, the project had no implemented plugin.
After
A button or command opens one read-only snapshot within the configured limit, rendered in full. The user invokes Accessibility Reader and presses Play.
Changes
Add the reader, settings-panel shortcut help and a saved 100,000-word default limit. Use normal Markdown rendering. README and docs/VISION.md explain the same benefits and limitations. Each Markdown pane has a top toolbar book icon that opens its own note.
Toolchain amendment, 2026-09-10
Node, npm and TypeScript were removed. The plugin is maintained as plain JavaScript.
Installation amendment
make install asks for the vault root, then puts the three maintained files in .obsidian/plugins/ios-tts/. Missing plugin directories are created; settings and unrelated files are preserved. The explicit PLUGIN_DIR route remains available for compatibility.
Unchanged
Obsidian owns rendering; Apple owns speech. The plugin does not edit notes, retain their contents, add network services or control audio.
Edge cases
Handle empty or unsupported notes, rendering errors, repeated invocation and closing during rendering without retaining stale content. Over-limit notes are refused, never truncated. Invalid settings retain the active limit; load failures use the default with a notice and no silent rewrite. Invalid install targets fail before copying; partial-copy errors are reported.
Decisions
Target Obsidian 1.13+, macOS 26+ and iOS 26+. Development stays outside the vault; installation uses an explicitly configured testing symlink or iOS copy.
Settings
Save only the word-limit preference in Obsidian plugin data. A Back button closes settings without saving unsubmitted input. Help covers triple-clicking the side/lock button, double-tap Back Tap, native speech without usage fees, and macOS setup. No system settings change.
Reader hint
Once rendering finishes, show a platform-specific shortcut hint beneath the title, outside the document article.
Accessibility amendment
Focus the document after rendering and make the surrounding workspace inert while the reader is open. Restore prior state on dismissal; native extraction still requires a reading check.
Distribution
Prepare Community directory copy and readiness guidance; actual release and listing submission follow release approval.
Evidence
Session and word-limit tests, native user tests on both platforms, and bounded package and security checks. Native user tests passed on 2026-09-16; see validation evidence.
Approval
Document approved 2026-09-08, including the interactive installer. See audit evidence and validation evidence.

Context

Problem and outcome

For long documents, Obsidian preview loads only a portion of the document for display. Accessibility Reader cannot access the unloaded content, so it cannot read the whole document.

The user needs the complete current Markdown note available to native Accessibility Reader, including content beyond the visible viewport. The plugin's responsibility is a full document presentation, not text-to-speech.

Scope

Included
One Open full document reader ribbon button and equivalent command, plus a book icon in each Markdown pane's top toolbar; one scrollable reader; one settings panel containing shortcut help and a maximum-word setting; README, vision and listing preparation.
Content
Pass the entire current Markdown source to Obsidian's public renderer. Preserve its normal body rendering, including links and embeds. Do not synthesize a separate filename title or properties panel, extract media text, expand links independently, or rewrite rendered content.
Excluded
Speech controls, custom Markdown parsing, export, EPUB/PDF conversion, live synchronization, background vault scanning, release publication, marketplace submission and automated vault deployment.
Unchanged
Existing editing, vault settings, other plugins and native accessibility configuration remain under their existing owners.

Acceptance Criteria

AC003.1 - Full current-note snapshot

Criterion
For an active Markdown note within the configured word limit in editing or reading mode, the reader buttons and command present its complete current rendered body in document order, including current editor changes. Empty content is valid. Opening again captures the current note, not the previous snapshot. A pane's toolbar icon opens that pane's note, including unsaved text, regardless of which pane previously had focus. Ribbon and command continue to use the active note.
Proven by
UT003.1 - macOS reading workflow and UT003.2 - iOS reading workflow.

AC003.2 - Complete native reading

Criterion
On each supported platform, for an accepted note within the configured limit, Accessibility Reader can discover and read the whole rendered document through its final text, without manually scrolling the plugin view to reveal missing text. Plugin controls do not interrupt the document's reading sequence.
Proven by
UT003.1 - macOS reading workflow and UT003.2 - iOS reading workflow.

AC003.3 - Source preservation

Criterion
Reader use provides no editing surface and causes no changes to source notes or their properties, including interaction with rendered task checkboxes. The plugin retains no note contents after the reader closes.
Proven by
UT003.1 - macOS reading workflow, UT003.2 - iOS reading workflow and OT003.1 - Source and security review.

AC003.4 - Single transient reader

Criterion
At most one current reader exists. A later invocation replaces the prior snapshot; closing or disabling the plugin releases its owned view and resources. Late rendering cannot reopen or replace a newer reader.
Proven by
RT003.1 - Reader session lifetime, UT003.1 - macOS reading workflow and UT003.2 - iOS reading workflow.

AC003.5 - Clear unsupported and failed states

Criterion
A missing or non-Markdown active note produces a brief notice requesting a Markdown note. A failed render produces a brief failure notice. Neither outcome shows stale or partially prepared content or alters a note.
Proven by
RT003.1 - Reader session lifetime, UT003.1 - macOS reading workflow and UT003.2 - iOS reading workflow.

AC003.6 - Native speech and existing access boundaries

Criterion
The plugin does not invoke speech, send note content to a service, save note content to storage or logs, or add privileged access or network operations beyond Obsidian's normal rendering of the same note. Presenting local text does not require a network connection, account or API key.
Proven by
OT003.1 - Source and security review and UT003.1 - macOS reading workflow and UT003.2 - iOS reading workflow.

AC003.7 - Platform lifecycle and accessible controls

Criterion
On both supported platforms, enabling the plugin makes its named button and command available without opening a reader or scanning documents at startup. The reader is scrollable and dismissible using the platform's normal pointer, touch or keyboard controls. Disabling and enabling again leaves one set of controls and Obsidian usable. The settings panel exposes a Back button operable by pointer, touch or keyboard that closes settings without saving unsubmitted input. Each Markdown pane has one named toolbar book icon, added to existing and newly opened panes and removed on plugin disable. Non-Markdown panes receive no icon. Reopening panes and re-enabling the plugin create no duplicates. Opening the reader isolates the surrounding workspace from interaction and accessibility navigation. Successful rendering focuses the document start, unless another foreground control has taken focus. Closing, failed rendering, replacement and unload restore the previous background state and return focus when the previous target still exists, without stealing focus from a newer foreground view.
Proven by
UT003.1 - macOS reading workflow, UT003.2 - iOS reading workflow and OT003.1 - Source and security review.

AC003.8 - Brief usable instructions

Criterion
The README identifies supported platforms, installation files and the open reader, invoke Accessibility Reader, Play flow, with links to Apple's setup instructions. The plugin settings panel contains bundled setup instructions and benefits/limitations, including triple-clicking the side/lock button, the Home-button alternative, double-tap Back Tap through Accessibility Shortcut, and the Mac shortcut. It explains native speech ownership, cloud-TTS costs, the word limit and normal-rendering boundary. README and docs/VISION.md present consistent claims and listing intent. Help remains readable offline; following an external link is optional. The rendered reader shows Mac Command-Escape guidance on the Mac desktop app, or accessibility shortcut guidance on iOS. The hint appears only after successful rendering, stays outside the document article and does not start speech. Mac wording allows for a customized shortcut; other platforms receive no platform-specific hint.
Proven by
UT003.1 - macOS reading workflow and UT003.2 - iOS reading workflow.

AC003.9 - Installable package and explicit destination

Criterion
The maintained package supplies main.js, manifest.json and styles.css for both supported platforms. Local installation writes only those three files into the explicitly supplied destination, preserves other files and skips copying artefacts whose contents already match. Invalid destinations fail before installation writes; an incomplete copy is reported as failure, never success.
Vault-root flow
Plain make install prompts for the Obsidian vault root and installs to its .obsidian/plugins/ios-tts/ directory, creating missing plugins/ and ios-tts/ directories. The root and its .obsidian/ directory must already exist. Blank input, EOF/cancellation and invalid roots produce an actionable non-zero failure without destination writes. Existing symlinks below the root are refused without replacement. Explicit PLUGIN_DIR continues to select the former non-interactive existing-directory route.
Proven by
OT003.2 - Build and local installation.

AC003.10 - Configurable maximum words

Criterion
Settings expose Maximum words, initially 100,000, and Save. A valid saved positive whole number persists across plugin reloads and applies to the next reader invocation. Invalid input or a failed save shows an actionable error and retains the active value. Missing settings use the default; malformed settings or a failed load use it with a notice, without silently overwriting stored data. Saving changes only this preference.
Proven by
RT003.2 - Word limit and preference, UT003.1 - macOS reading workflow, UT003.2 - iOS reading workflow and OT003.1 - Source and security review.

AC003.11 - Explicit refusal above the word limit

Criterion
A note at or below the configured limit remains eligible for complete rendering. A note above it clears any previous reader and receives a notice identifying the limit and explaining how to raise it in settings. It is not rendered or truncated. The check uses the full current Markdown source, counting each whitespace-separated non-empty token as one word; properties and markup count, and empty source counts as zero.
Proven by
RT003.2 - Word limit and preference, UT003.1 - macOS reading workflow and UT003.2 - iOS reading workflow.

Solution Design

Architecture and flow

  1. Load and validate the word-limit preference, then register the ribbon button, command and settings tab through Obsidian's Plugin API. Add a toolbar book icon to each Markdown pane once the layout is ready. Perform no document work during plugin startup.
  2. Capture the active MarkdownView, its file path and getViewData() once before asynchronous work. Validate a present Markdown file; do not read a disk copy in place of current editor contents. Capture the current saved limit too. Clear the prior session and check the source word count before rendering; over-limit input receives the settings guidance notice.
  3. Close the previous reader and open a dismissible Obsidian Modal with a preparing notice. Render the whole captured source into one detached article using MarkdownRenderer.render and a session-owned Component. Pass the captured source path for normal relative references.
  4. After rendering succeeds, replace the preparing notice with the complete, scrollable article. Do not use preview sections, virtualization, folding or lazy body rendering. Keep the close control outside the article. Disable task editing controls without hiding the article from accessibility.
  5. The user invokes Apple's Accessibility Reader. Closing, replacing or unloading invalidates the session, detaches the article and unloads its component. Late success or failure cannot publish into a later session.

Interfaces and state

Structure
One maintained main.js with the existing settings, session and Obsidian adapter classes, plus manifest and stylesheet. No bundler, compilation, dependency installation or runtime library.
Language
Plain JavaScript with a CommonJS plugin-class export. Obsidian supplies require("obsidian"); no Node/Electron API is imported.
Commands
make install and make sync use Bash. make test executes the same 12 behavioural tests using macOS osascript. A small test-only prelude supplies inert host base-class names to load the real package; no Obsidian UI or native reader is instantiated or simulated. make lint uses native oxlint/Biome and ShellCheck/shfmt, which are not installation prerequisites. Scripts support stock macOS Bash 3.2 to avoid an extra installation dependency.
Toolbar
Use the public MarkdownView.addAction() API with ios-tts-accessibility-reader and the name Open full document reader. Keep a map of views to their button elements. Reconcile against loaded Markdown views on layout readiness, layout-change and file-open; remove controls for closed views and all controls on unload. Register events through the plugin lifecycle, and ignore a late layout-ready callback after unload. Capture the owning view in each callback but read its current text only on activation. No note contents are read just to add a toolbar control.

Preserve the supplied SVG as a source asset; use its book-and-sound-waves artwork in both toolbar and ribbon controls. Removed targets

make build and the npm-based make vulncheck are removed: the project has neither compilation nor a package-managed dependency graph. A future dependency requires explicit approval and an applicable security check.

Package
main.js, manifest.json and styles.css form the plugin. Use manifest identifier ios-tts, minAppVersion: 1.13.0 and isDesktopOnly: false. README documents the additional OS requirements.
Installation
make install runs scripts/install.sh without a build. Unless PLUGIN_DIR is non-empty, prompt for the vault root, trim the input, allow optional matching surrounding quotes and expand leading ~/ using the existing shell home-directory value. Require an absolute existing directory and resolve that explicitly selected root canonically. Require an existing real .obsidian/ directory. Blank input, EOF and Ctrl-C abort. Bash read failure and interrupt signals abort before copying.
Compatibility
make install PLUGIN_DIR=/absolute/plugin/directory keeps its non-interactive explicit existing-directory semantics, including an explicitly selected directory symlink. This route does not prompt or create directories. Both modes validate all artefacts before any copy: each must be absent or a regular file, never a symlink or directory. Fixed artefact basenames stay within that canonical destination; no recursive copy is allowed. The prompt route creates missing directories only after validation. Report the installed destination and remind the user to enable the plugin in Obsidian. Print the disabled-plugin prerequisite before prompting.
Replacement
Replace only changed artefacts and preserve all other files. Installation requires the plugin disabled. Individual copies are not a transaction: an I/O error exits non-zero, reports possible partial installation and directs a retry before re-enabling. Do not replace or remove the whole destination directory. The copy step leaves identical files untouched; the checkout's files are maintained source.
Symlink workflow
If the canonical destination is the checkout itself, the maintained artefacts are already exposed through the configured symlink; verify the three files and skip copying. iOS receives the same files through the existing vault synchronization process. Never edit the enabled-plugin list.
Settings
Use Obsidian's PluginSettingTab and Setting controls for one Maximum words field and Save. Accept trimmed decimal digits representing a positive safe integer; reject other input rather than coercing it. Use loadData() and saveData() for { maxWords: 100000 }; persist no note data. Disable Save while a write is pending and update the active limit only after success. On failure retain it and show a retryable error. A missing setting defaults normally; malformed data or a rejected read defaults with a notice and no write until an explicit valid Save. Use host-managed storage only. Ignore its data.json in Git during symlink testing; installation preserves it.
Settings navigation
A semantic button labelled Back precedes the field. Its click listener belongs to the settings render owner. Use the host's internal app.setting.close() method, capability-checked because the public SettingTab API exposes no close operation. If unavailable, show a notice directing the user to Obsidian's close control. Native platform tests verify actual dismissal; a simulated host would not establish that contract. No new automated test or framework is justified for this native UI action.
Admission
Count non-empty whitespace-delimited tokens in captured Markdown source, including properties and markup. A linear scan may stop as soon as it exceeds the captured limit. Do not allocate a second whole-document token array or expand embeds just to count. Invalid/over-limit input clears the previous reader without invoking the renderer.
Help
Preserve the existing Markdown help as a readable literal in main.js, using the same host renderer and cleanup. docs/reader-help.md is its documentation counterpart; review both together and compare their text when either changes. This replaces the build-time import to keep the three-file offline package without a runtime read or download.

Security impact

Threat boundary
Note content enters Obsidian's existing Markdown renderer. Do not insert untrusted HTML manually or add executable processors.
Existing rendering
Normal embeds, remote resources and installed Markdown processors remain host behaviour. This plugin is not a sandbox and does not promise that arbitrary third-party rendering is offline or read-only. The supported user-test baseline uses only core plugins and local fixtures.
Data and access
The plugin adds no external service, content logging, durable content storage, credentials or privileged host API. Do not change the user's system settings or vault permissions. Save only the validated word-limit number through Obsidian's plugin storage. The word limit reduces oversized-text rendering attempts; it is not a byte-size limit or a defence against arbitrary embedded content.
Dependencies
Only Obsidian's host API is required. There is no application- managed dependency graph, lockfile, downloaded runtime or build dependency. Native developer linters are not distributed with the plugin.
